# Structured prompt engine

`structured-web-v1` lives in `src/prompts.ts`. This tunes instructions and examples;
it does not train new model weights. The same output contract is used by the
document model and the faster chat model, so presentation and case memory do not
depend on each model inventing its own format.

## What a reply looks like

Answer the question in one or two reassuring, practical sentences, then include
a specific next step and the right contact. Ask at most one missing question.
Include a draft only when useful or requested. For example, after a user gives
a $30 monthly budget for a $180 statement:

> I can help you prepare a request for $30 monthly installments.
>
> At 30.00 USD per month, the 180.00 balance would take 6 payments, before fees
> or new charges. The biller needs to accept the proposal.
>
> Next step: Ask the billing office to accept $30 monthly payments and confirm
> whether an accepted arrangement affects the notice deadline.
>
> Who to contact: Example Electric’s billing/customer assistance team. Use the
> statement or official website; a current number or email still needs verification.
>
> What date would work for your first payment?

These are proposed terms, not an accepted arrangement. The live wording varies;
the backend supplies the math, contact provenance, and status boundaries.

## Extraction and evidence

The extraction instruction returns a separate record for each statement, invoice,
EOB, or notice (up to 12). Each record includes:

- Biller, document/bill type, statement date and service period.
- Amount due, overdue balance, charges, payments and adjustments as distinct fields.
- Due, shutoff and collections dates as distinct fields; unknowns remain `null`.
- Statement-specific line items, printed terms, contacts, source quotes and pages.
- Uncertainties such as unreadable text, repeated notices or conflicting figures.

Amounts from multiple statements are not summed into a top-level debt. An EOB
does not establish a payable balance. Quotes attached to description-based facts
must occur in the submitted description; contact values must occur in their quote.
Document quotes are generated by Gemini and are not independently checked against
OCR. A page number is a source reference, not proof of extraction accuracy.
The large extraction schema sends its shape, types, enums and required keys to
Gemini; length/range/pattern constraints remain in runtime Zod validation to avoid
provider schema-complexity rejection. Google documents this limit in its
[structured-output guide](https://ai.google.dev/gemini-api/docs/generate-content/structured-output).

Legacy saved bills work without re-uploading. A source-detail question can trigger
rereading the retained document and save newly found contacts/terms. Ordinary
questions use saved facts instead of processing the document on every turn.

## Remembered case and response contract

SQLite persists the user’s goal, budget, first payment date, chosen statement,
service location, reported prior contact/agreement, corrections and confirmations.
It also stores the last clarification question and current intake description.
Memory remains available after the most recent ten chat turns are truncated.
New uploads replace the active document and reset old statement-specific facts;
global user circumstances remain. The original intake description does not get
mixed into the new bill. STOP removes the active case and associated replies.

The model returns `intent`, `answer`, optional `concern`, `supportingStatementIds`,
`nextStep`, `contact`, optional `question`/`draft`, `needsDocument`,
`needsPolicyLookup`, and `caseUpdates`. Responses are validated by Zod. Each memory
patch needs an exact quote from the current message or intake; unsupported patches
are ignored while existing memory remains. An intake fact cannot overwrite a later
user correction. Confirmations must match the previous question and statement.

The backend:

- Applies user corrections without overwriting the original extracted evidence.
- Calculates installment counts in cents, excluding fees and new charges.
- Suppresses questions already answered, and requires statement selection before
  a payment proposal for a packet with unconfirmed separate balances.
- Displays document-provided contacts as unverified current. If none exists,
  identifies billing, financial assistance, insurer member services, property
  management or the contact on a collections notice without guessing details.
- Rejects unknown references, unsupported phone/email/URL details and common
  unsupported outreach/approval claims. These checks are not a semantic proof
  that every free-text assertion is correct.
- Handles common “have you contacted/sent…” questions directly from application
  state without a model request. No outreach tools are currently connected.
- Prioritizes explicit action dates within three days. A statement more than
  90 days old prompts confirmation of current status. These are product heuristics,
  not legal deadlines or protections. A past action date does not prove it occurred.

`needsPolicyLookup` and a public `researchQuery` route to a separate Gemini Google Search request, followed by structured synthesis. Only cited excerpts and supplied source URLs authorize additional contact details. Equivalent phone formatting is accepted; unsupported contacts get one repair attempt, then a fixed fallback with source links. A contact emitted without a lookup flag can also trigger public research. Failed/unattributed lookups use an application-generated fallback instead of legal claims from model memory. Source attribution does not establish eligibility or guarantee a rule applies.

Approved scheduled check-ins and optional read-only Gmail alerts are separate application features; see [their guide](follow-ups-and-email.md). Outgoing biller email, negotiation and confirmed holds are not implemented.

## Minimum questions and checks

| Question | Required behavior |
| --- | --- |
| What does this bill say? | Explain the statement’s balance, date, notice and uncertainty. |
| What do I owe? | Separate charges, payments and current stated balance. |
| When must I act? | Distinguish payment and explicit action deadlines. |
| Will a partial payment stop action? | Confirm terms with the biller; no guarantee of a pause. |
| Why is it high? | Explain printed line items; request missing detail rather than assert an error. |
| Are these separate bills? | Preserve separate records and flag possible overlap. |
| Can I pay in installments? | Use a known budget or ask for one; prepare a proposal. |
| I can afford $X—what should I ask? | Compute payments and ask about start date/terms. |
| Could I get assistance? | Identify the assistance team and missing eligibility facts. |
| Is this EOB payable? | Compare with the provider statement and insurer processing. |
| How do I dispute it? | Prepare a specific itemization/review request. |
| Who do I contact? | Printed contact or cited public research; department guidance when a detail cannot be supported. |
| Can you draft the request? | Ready-to-send user draft, explicitly unsent. |
| What rules apply here? | Research current company/local sources, cite them and clarify service jurisdiction/applicability. |
| What have you done? | Honest application status; no invented email, hold or agreement. |
| The amount/date changed | Save a scoped user correction and preserve original source evidence. |
| This is an old notice | Confirm current balance/status instead of announcing an imminent action. |

From the repository root:

```sh
./run.sh --check
# Live API requests using fictional data, no Photon messages:
npm run gemini:check -- --chat-only --show-structure
npm run gemini:eval
# Optional selected cases:
npm run gemini:eval -- installments action-status historical-notice
```

The live evaluator covers 17 fictional cases, spaces requests for development
quotas, reports latency and checks structure plus selected facts. API charges
apply. It fails on failed checks or API errors. Read each response against its
printed criterion: a passing structural check alone does not establish accuracy,
empathy or model quality. Automated tests use mocked responses and exercise
persistence, isolation, migration, duplicates, source/contact boundaries and math.

To tune this further, change the versioned prompt/examples, rerun the fictional
evaluation, inspect the wording, then try consented real-world samples. Compare
latency and usefulness when changing models. Weight fine-tuning can be evaluated
later if the selected model supports it and the examples justify it.
